# Architecture

## Design boundaries

AgentFlow is one trusted operator workspace. A browser never connects directly to privileged Supabase tables. Next.js owns authentication, validation, business rules and encrypted configuration. n8n owns the shared customer AI Agent and its model/memory/tool graph. A native Node worker owns slow jobs and outgoing provider delivery. PostgreSQL is the durable source of truth.

The product deliberately does not claim that four channel adapters are four independently tested agents. All connected channels share the same agent policy and tools while retaining separate customer contexts.

## Customer message lifecycle

1. Website requests carry a signed HttpOnly customer-session cookie. External webhooks verify provider signatures/secrets; polling and Socket Mode use provider-issued tokens.
2. A channel adapter normalizes the event into a channel, account, stable conversation key, provider event ID, text, target and optional media metadata.
3. One database transaction creates/reuses the conversation, deduplicates the inbound event and stores an inbound job. Only then does the webhook acknowledge receipt.
4. The worker takes a durable job. Human-controlled conversations bypass AI. The explicit `/human` command is handled without asking a language model.
5. The worker calls the n8n webhook with a short-lived signed conversation capability. That capability is fixed by the application, not generated by the model.
6. The actual n8n AI Agent uses Gemini, Postgres history and authenticated HTTP tools. It can retrieve knowledge, save its own lead, check slots, book and request handoff.
7. Tool writes re-check the conversation version under a database lock. Booking uses transactional idempotency plus a database exclusion constraint.
8. Agent output is queued for delivery. A final mode/version check suppresses stale AI responses after human takeover. Provider IDs and delivery states are recorded separately from generated text.

## Data model

`conversations` separates provider accounts and identities. `messages` records inbound/outbound direction, author, provider ID and state. `leads` keeps customer-provided facts, consent, an explicit completeness score and separate AI advisory enrichment. `appointments` reserves one consultant resource with non-overlapping confirmed time ranges. `handoffs` allows one open handoff per conversation. `activity` stores operator notes and business events.

`knowledge_documents` and `knowledge_chunks` hold source text, model provenance and 768-dimensional embeddings. `chat_memory` is dedicated to n8n's Postgres memory node. `jobs`, `runtime_state`, `rate_limits`, `workflow_runs`, `channel_status` and `intake_events` support execution, idempotency and observability. `automation_items` stores drafts/extractions and reviewed export status.

## Identity and privacy

Telegram keys include bot/account and private chat. Slack keys include workspace, customer, channel and thread; unthreaded DMs retain the same conversation across messages. WhatsApp keys include the business phone account and sender. Website customers receive server-created UUIDs. Identities across channels are not merged merely because names or email addresses look similar.

Only the operator may browse the inbox or CRM. Customer tools derive the permitted lead from their signed conversation context; a model-supplied lead ID cannot switch customers. Provider content and retrieved knowledge are untrusted data, never authorization instructions.

## Knowledge retrieval

Text is normalized and split into 1,200-character chunks with 180-character overlap. Gemini creates normalized 768-dimensional embeddings. Retrieval filters by embedding model, selects the five nearest chunks and applies an initial cosine-similarity threshold of 0.35. This threshold is a project default, not a scientifically validated confidence guarantee. Tune it against a business-specific evaluation set.

The returned document title/source ID should ground answers. No matching evidence requires an honest fallback. Prompt instructions reduce hallucination risk but do not guarantee it is eliminated. Changing embedding models requires re-indexing documents.

## Reliability trade-offs

The initial worker is intentionally single-process and uses a PostgreSQL advisory lease. It keeps installation small and ordering understandable but is not horizontally scaled. Use the Supabase session pooler or a direct session connection, not the transaction pooler. Completed jobs erase their payload; failed jobs retain diagnostic input and require a retention policy before production.

Retries use bounded backoff for transient failures. An outbound timeout may happen after a provider accepted a message. Such deliveries become `unknown`, not automatically resent. A network/provider API cannot guarantee exactly-once delivery in every failure window; reconcile unknown deliveries before another send.

The worker's single queue can delay unrelated conversations during a slow AI call. Large-scale deployment needs partitioned workers, stronger distributed scheduling, operational limits and measured load tests.

## Business policy

Default appointment policy: Asia/Aden, Sunday–Thursday, 09:00–17:00, 30-minute slots, up to 90 days ahead, one consultant. Confirmation must come from the customer or operator. This is an internal calendar, not an external-calendar integration.

Lead completeness points: email 20, business need 25, company 15, budget 20, timeline 20. AI enrichment is advisory and separate. Scores do not infer demographic traits or consent.

Follow-ups select consented new/qualified/contacted leads inactive for two days and create reviewable drafts. Message triage and invoice extraction similarly require human verification before sending/exporting. Structured JSON validation is necessary but does not establish factual accuracy.

## Deployment

Use separate development provider accounts, one project per fair comparison run and loopback-only application/n8n ports. Public HTTPS ingress exposes only `/api/hooks/whatsapp`, `/api/hooks/telegram`, `/api/hooks/slack`. Production deployment requires a separate threat review, HTTPS session settings, secrets management, role-based access, backups, data retention and monitoring.
